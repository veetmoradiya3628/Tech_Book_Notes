
- Data lakes and data warehouses, setting the stage for modern data lake house architecture on Google Cloud.
- Data lakes and data warehouses
	- Data lakes
		- data lake as a vast reservoir of data
		- It stores enormous amounts of raw data in its native format
		- any kind of data can be poured - structured, semi-structured, unstructured
		- "store everything now, figure out how to use it later"
		- schema-on-read
		- Advantages
			- Flexibility
			- Agility
			- Scalability
			- Cost-effectiveness
			- Support for advanced analytics
		- Disadvantages
			- Risk of becoming a "data swamp"
			- Management complexity
			- Time-consuming analytics
			- Security risks
	- Data warehouses
		- highly organized library. data is cleaned, transformed, and structured before it's stored. This process, known as schema-on-write, ensure the data is optimized for analytics and business intelligence (BI).
		- "structure and quality first"
		- The intended use of the data must be determined before the warehouse is designed.
		- data warehouses are perfect for generating business reports and dashboards where speed and accuracy are critical.
		- Advantages
			- Speed
			- High-quality data
			- Business-focused
			- Historical intelligence
		- Disadvantages
			- Inflexibility
			- Cost
			- Limited data types
			- Long development time
- The modern approach: Data lake house
	- Ideal approach combines the flexibility and low cost of a data lake with the speed and accuracy of a data warehouse. this hybrid approach has created the concept of a data lake house.
	- A lake house achieves this by implementing a metadata and governance layer on top of open-format files stored in low-cost object storage, like Google Cloud Storage. This gives you the best of both words.
	- Key features
		- Support for most data formats
		- Flexible schema-on-read or schema-on-write
		- Access for all types of data users
		- cost flexibility based on needs
		- Unified data governance
		- ACID transaction support
	- Google cloud implements data lake houses through Big Lake technology
- Consider a data warehouse, like BigQuery when the primary need is high-speed, interactive BI on structured business data, such as for Cymbal's finance department.
- Consider a data lake, using Cloud Storage, for the initial, low cost storage of massive volumes of raw data. This is ideal for Cymbal's AI/ML research and development where the data's final use is not yet defined.
- Adopt a data lakehouse architecture with BigQuery and BigLake when you need to do it all.

- BigQuery
	- Enterprise grade, fully managed, serverless data warehouse
	- BigQuery separates storage from compute
	- Distributed processing engine called Dremel
	- Slots and shuffle
		- Slot
			- Virtual worker
			- a small, self-contained unit of computational power that includes CPU, RAM and network bandwidth.
			- massively parallel processing
		- Shuffle
			- Shuffle is the process of redistributing the intermediate data that the slots have processed. 
	- BigQuery's ground breaking separation of compute and storage is the key to its versatility in querying data from multiple sources. Think of the compute engine, Dremel as a flexible data analyst that is not tied to a single filling cabinet.
	- For native BigQuery tables, Dremel directly and most efficiently reads from its highly optimized columnar storage files in the Colossus intelligent file system.
	- Partitioning and clustering
		- Partitioning
			- Partitioning is like adding dividers to a filling cabinet. Instead of one giant drawer, you have separate sections for each year, month, or day. In BigQuery you can partition a table based on a date or an integer column.
			- Partition reduces scan scope of the table and improves overall query performance
		- Clustering
			- While partitioning divides the data into large chunks, clustering  sorts the data within each of those chunks. Think of its as organizing the files within each drawer of your filling cabinet alphabetically by customer name.
	- BigQuery works differently depending on whether you're using its native tables or external Apache Iceberg tables stored in Cloud storage.
	- Final principle - `Use metadata to skip unnecessary data, so queries run faster and cost less`

- BigLake and external tables
	- BigLake acts as a storage engine and connector that allows your to extend the capabilities for BigQuery to your data in object storage, like  Google cloud storage. BigLake lets you create tables in BigQuery that do not hold the data themselves but instead point to the data files living in your data lake. These are called `external tables`
	- open standards
		- Lakehouses rely on open, standarized formats to avoid lock-in and ensure interoperability.
