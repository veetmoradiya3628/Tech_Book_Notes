- Sources & Sinks
	- Source - Reading input data
	- Sink - Writing output data
	- Bounded sources - Sources that read a finite amount of input
	- Split the work of reading into smaller chunks, known as bundles
	- Provide estimates of progress to the service and number of bytes to be processed.
	- Unbounded source - Source that reads an unbounded amount of input (e.g streaming)
	- Allowing for the source to not re-read the same data by using checkpoints.
	- Providing data to the service on what point in time the data is complete by using watermarks
	- Deduping the data with the option to mark use of Record IDs from the unbounded source
	- Sinks are often "normal" PTransforms that write data to end systems

- State and Timers
	- State API
		- stateful ParDo/Map
		- Persistent mutable state
		- Buffer state and Count state
		- Aggregation in ParDo using state variables
	- Timer API
		- Event-time timers
			- Callback when the watermark reaches some threshold.
			- Output based on data completeness of input data
		- Processing-time timers
			- Callback after a certain amount of time has elapsed.
			- Timeouts
		- Timers are used in combination with state variable to ensure that the state is cleared at regular time intervals

- Best Practices
	- Schemas
	- Handling erroneous data
		- Our pipeline should handle erroneous data to put in DL sink
	- Error handling
		- Errors and exception are part of any data processing pipeline
		- Always put try-catch block where ever required
		- Tuple tag and catch block error data send to separate sink
	- Auto Value code generator
		- POJO is needed in Java data pipeline
		- Use the AutoValue class builder to generate POJOs when not using Beam Schemas
	- JSON data handling
		- JsonToRaw - helper class used to convert JSON strings into Java POJOs in Dataflow
	- Utilize DoFn Lifecycle
		- DoFn for micro batching
	- Pipeline optimizations
		- Filter data early in pipeline whenever possible
		- Move any steps that reduce data volume up in your pipeline
		- Apply data transformations serially to let Dataflow optimize DAG
		- Transforms applied serially are good candidates for graph optimization because multiple steps can be fused in a single stage for execution in the same worker node.
		- While working with external systems, look out for back pressure
		- Ensure external system are configured to handle peak volume
		- Enable autoscaling to downscale if workers are underutilized
