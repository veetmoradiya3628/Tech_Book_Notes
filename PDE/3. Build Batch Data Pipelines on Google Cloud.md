
- As a data engineer, the core of your role is to build reliable pathways for data to move from raw sources to valuable insights. 
- batch data pipeline: These pipelines are the backbone of enterprise data strategy, responsible for processing large, finite datasets that are critical for everything from daily financial reconciliation to strategic business analytics.

- batch data pipelines
	- A batch data pipeline is a sequence of processes on one or more sets of data, designed to ingest, transform, and sink that data, in large, discrete chunks, or "batches", at scheduled intervals.
	- use cases
		- Periodic reporting
		- Large scale transformations
		- Data warehousing
		- Data migration
		- Scheduled backups
- components and stages
	- Data sources
		- Origin of your raw data, which can come in various formats (CSV, JSON, database tables, log files etc)
	- Data Ingestion
		- from source to 'landing zone' or 'staging area'
	- Data Transformation
		- Ingested data may be cleaned, validated, enriched, mapped, and/or restructured into a consistent and standardized format, before landing in the destination sink.
	- Data Sink
		- Final store
	- Downstream Uses
	- Orchestrate and Monitor

- Batch processing vs. batch pipelines
	- Batch data processing
		- The method or technique of handling data. It's about collecting data over a period (a "batch") and then processing that entire batch in a single, scheduled run.
	- Batch data pipelines
		- The entire automated system or infrastructure that implements batch data processing. It's the series of interconnected stages that systematically move and process data in batches from source to destination.
- Key features of batch data processing
	- Scheduled and automated
		- periodic execution jobs should have scheduled and automated nature
	- High throughput
		- rapid processing of large quantity of data records.
	- Latency
		- latency is allowed as this is "offline" behavior
	- Resource optimization
		- "burst" resource consumption

- Schema evolution for batch pipelines
	- For batch pipelines, you can not update a running job. therefore, handling a schema change means deploying a new version of your pipeline that can process the new data structure correctly on its next scheduled run.
	- Common challenges
		- Additive (non-breaking)
		- Breaking
	- Schema-on-write vs. Schema-on-read
		- Schema-on-write
			- The schema is strictly enforced when the pipeline tries to write the data.
			- BigQuery operates on this model, requiring data to conform to a predefined table structure
		- Schema-on-read
			- Data is stored in its raw format, often in files like JSON or CSV in a cloud storage data lake.
			- The structure is flexible, and a schema is only applied when the pipeline reads the data
	- What is `data swamp` ?
	- The strategy
		- Most of the time `schema-on-write` is chosen
		- Two approach
			- Reactive management
				- This approach uses pipeline features to handle simple, addictive changes automatically at runtime.
			- Proactive management (Schema as Code)
				- This is a more robust strategy where schema definitions are stored in version control (like git) and managed through a formal review process.
- A process flow for schema evolution
	- Initial state
	- Spark logic
	- Execution engine
	- Table modification
	- Final state
	- Validation

- Data Integrity and duplication
	- Cleaning the dataset of duplicate records.
	- Duplication of records types
		- Exact duplicates
		- Key based duplicates
		- Semantic duplicates
	- Dataflow: From GroupByKey to CombineFn
		- beam.Distinct()
		- Hot key problem
			- GroupByKey works by shuffling all values for a given key to a single worker. If one key has billions of records, that worker becomes a massive bottleneck and can fail the entire job.
		- Two state aggregation as a solution
			- pre-shuffle
			- post-shuffle
		- CombinePerKey vs. GroupByKey
	- Deduplication in Spark: the window function
		- When you need to perform key-based deduplication in spark batch jobs, the goal is to reliably and efficiently select just one record for each key. The industry-standard and most robust pattern for this task is using a window function.
	- Semantic deduplication
		- Semantic deduplication is an analytics workload, not an ETL task.
		- Best handled in BigQuery with BigQuery ML
		- human-in-the-loop principle
